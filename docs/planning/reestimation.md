# Re-Estimation Protocol

Project: Calorie Counter Telegram Bot
Team: Team 4 (COMP 330, Fall 2026)
Owner: Sohail (Quality & Review Lead)

## 1. Purpose
Initial task estimates are just starting guesses. As we actually start coding the Telegram bot and hooking up food APIs, some tasks will take longer or shorter than we thought. This document explains when and how our team adjusts estimates and updates the schedule so we do not fall behind.

## 2. When We Re-Estimate
We revisit an estimate if any of these happen:

- A task is taking way longer than expected (for example, spending 4 hours on something estimated for 2 hours and it is not close to done).
- We hit unexpected technical issues, like API rate limits, Telegram webhook problems, or tricky library bugs.
- We discover missing work that was not in the original task list.
- A team member gets sick or has a major schedule conflict, affecting our 48-hour internal deadline.
- Feedback from the professor requires rework on an existing deliverable.

## 3. How We Handle It
When someone realizes a task is off track, here is the process:

1. Flag it early: Post in the team group chat and leave a comment on the GitHub issue explaining the blocker. Do not wait until the day before the deadline.
2. Discuss at standup: The task owner talks with Bazid (Planning Lead) and the team during our weekly check-in or a quick sync to figure out what is left.
3. Update the numbers: Update the hours in estimates.md and on the GitHub Project board. Keep the original estimate next to the new one so we can see the difference.
4. Adjust scope if needed: If the delay risks missing the deadline, we check deferred-scope.md and move non-essential features (like advanced macro tracking or extra message formatting) to a later cycle.
